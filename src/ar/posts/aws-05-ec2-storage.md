## أقراص EBS

**EBS** (Elastic Block Store) قرص شبكي توصله بالسيرفر. يتصرف مثل قرص عادي، لكنه مستقل عن السيرفر، فبياناته تبقى حتى لو حذفت السيرفر. وهذا القرص اللي يقلع منه سيرفرك غالباً.

أهم شي تعرفه عنه:

- **مربوط بمنطقة توفر واحدة.** قرص في `eu-central-1a` ما يتركب مباشرة على سيرفر في `eu-central-1b`.
- **لسيرفر واحد في الوقت** عادةً، والسيرفر الواحد يقدر يركّب كذا قرص. والاستثناء ميزة Multi-Attach في أقراص `io1` و`io2`، داخل نفس منطقة التوفر، وتحتاج نظام ملفات يفهم هذا.
- **الحذف مع السيرفر:** قرص النظام ينحذف مع السيرفر افتراضياً، والأقراص الإضافية تبقى. وتقدر تغيّر هذا من إعداد **Delete on Termination**.
- **تدفع على المساحة المحجوزة**، مو المستخدمة.

### أنواع الأقراص

| النوع | وصفه | يناسب |
| --- | --- | --- |
| `gp3` | SSD عام، تحدد سرعته مستقلة عن حجمه، ويبدأ من 3000 IOPS | الخيار الافتراضي لأغلب الحالات |
| `gp2` | SSD عام أقدم، سرعته مرتبطة بحجمه | الأنظمة القديمة، واختر `gp3` بدله |
| `io2` / `io1` | SSD بأداء عالٍ مضمون | قواعد البيانات الحرجة |
| `st1` | قرص صلب سريع النقل، رخيص | البيانات الضخمة والسجلات |
| `sc1` | قرص صلب للبيانات الباردة، الأرخص | أرشيف نادر الوصول |

**IOPS** عدد عمليات القراءة والكتابة في الثانية، وهو اللي يهم قواعد البيانات. و**Throughput** كمية البيانات المنقولة في الثانية، وهو اللي يهم الملفات الكبيرة. والأقراص الصلبة (`st1` و`sc1`) ما تصلح أقراص إقلاع.

### اللقطات (Snapshots)

**اللقطة** نسخة احتياطية من القرص في لحظة معينة. تحفظ التغييرات فقط بعد أول لقطة، فتوفّر في التكلفة. وتقدر من اللقطة تنشئ قرص جديد في **أي منطقة توفر**، أو تنسخها لمنطقة ثانية. يعني هي الطريقة الصحيحة لنقل قرص بين مناطق التوفر.

وفيه ميزتين تفيدك: **Recycle Bin** يحميك من حذف لقطة بالخطأ، و**Archive** يخفّض تكلفة اللقطات اللي نادراً ترجع لها.

### التشفير

فعّل تشفير EBS: البيانات على القرص والنقل بينه وبين السيرفر واللقطات كلها تتشفّر بمفاتيح KMS، بدون أي تغيير في تطبيقك وبأثر بسيط على الأداء. وتقدر تفعّله افتراضياً لكل الأقراص الجديدة في المنطقة من إعدادات EC2.

وتشفير قرص موجود غير مشفّر يمر بخطوات: تسوي له لقطة، تنسخها مع تفعيل التشفير، ثم تنشئ من النسخة قرص جديد مشفّر، وتركّبه بدل القديم.

## صور النظام (AMI)

**AMI** صورة جاهزة يقلع منها السيرفر: نظام التشغيل والبرامج والإعدادات. عندك ثلاثة مصادر: صور AWS، وصور AWS Marketplace الجاهزة من شركات ثانية، و**صورك أنت**.

الفكرة اللي تفرق: بدل ما كل سيرفر جديد يثبّت كل شي من أول عن طريق User Data، جهّز سيرفر مرة وحدة وخذ منه صورة:

```bash
aws ec2 create-image \
  --instance-id i-0123456789abcdef0 \
  --name "web-nginx-v1"
```

الحين أي سيرفر يقلع من هذي الصورة يقوم جاهز خلال ثوانٍ بدل دقائق. وهذا مهم جداً في التوسّع التلقائي. لاحظ إن الصورة مربوطة بمنطقة واحدة، وتقدر تنسخها لمناطق ثانية.

والنمط الشائع: صورة فيها الأشياء الثابتة والثقيلة، وUser Data خفيف للإعدادات اللي تختلف من سيرفر لسيرفر.

## التخزين المحلي (Instance Store)

بعض أنواع السيرفرات فيها قرص فعلي **داخل الجهاز نفسه**. هذا **Instance Store** أسرع بكثير من EBS، لكنه مؤقت: بياناته تروح لو أوقفت السيرفر أو حذفته أو تعطّل الجهاز. وتبقى مع إعادة التشغيل العادية (Reboot) فقط.

يناسب الكاش والملفات المؤقتة والبيانات اللي لها نسخ في مكان ثاني، ولا تحط فيه شي ما تقدر تخسره.

## نظام الملفات المشترك (EFS)

**EFS** (Elastic File System) نظام ملفات شبكي يتركّب على **عشرات أو مئات السيرفرات في نفس الوقت**، وعبر مناطق توفر مختلفة. يكبر ويصغر تلقائياً، وتدفع على اللي تستخدمه فعلاً.

يناسب المحتوى اللي لازم كل السيرفرات تشوفه، مثل ملفات المستخدمين المرفوعة في موقع يعمل على كذا سيرفر. وله شرطين: **يعمل مع لينكس فقط**، وسعره أعلى من EBS للجيجا الواحدة. ولتوفير التكلفة، فعّل سياسة دورة الحياة عشان تنتقل الملفات اللي ما تُستخدم لفئة أرخص تلقائياً.

تركيبه على سيرفر:

```bash
sudo dnf install -y amazon-efs-utils
sudo mkdir -p /mnt/shared
sudo mount -t efs fs-0123456789abcdef0:/ /mnt/shared
```

::: tip لو علّق أمر mount
EFS يستخدم المنفذ 2049. لازم مجموعة أمان EFS تسمح بـ NFS على هذا المنفذ من مجموعة أمان السيرفرات. وهذا تطبيق لما شرحناه عن الإشارة لمجموعات الأمان في [الجزء الثالث](/posts/aws-03-ec2-first-server/).
:::

## أيهم تختار؟

| | EBS | Instance Store | EFS |
| --- | --- | --- | --- |
| **النوع** | قرص شبكي | قرص محلي | نظام ملفات شبكي |
| **المشاركة** | سيرفر واحد غالباً | سيرفر واحد | مئات السيرفرات |
| **النطاق** | منطقة توفر واحدة | الجهاز نفسه | عبر مناطق التوفر |
| **البيانات بعد الإيقاف** | تبقى | تضيع | تبقى |
| **الأنظمة** | لينكس وويندوز | لينكس وويندوز | لينكس فقط |
| **مثال** | قرص النظام، قاعدة بيانات | كاش سريع | ملفات مشتركة |

## عملي: أضف قرص وخذ منه لقطة

شغّل سيرفر في منطقة توفر معروفة، ثم نفّذ هذا من CloudShell:

```bash
# قرص 10 جيجا مشفّر في نفس منطقة توفر السيرفر
aws ec2 create-volume \
  --availability-zone eu-central-1a \
  --size 10 --volume-type gp3 --encrypted

# ركّبه على السيرفر (استبدل المعرّفات بالقيم عندك)
aws ec2 attach-volume \
  --volume-id vol-0123456789abcdef0 \
  --instance-id i-0123456789abcdef0 \
  --device /dev/sdf
```

وداخل السيرفر، جهّزه واستخدمه:

```bash
# اعرف اسم القرص الجديد، غالباً nvme1n1
lsblk

# تنسيق القرص: يمسح كل ما فيه، فاستخدمه مع قرص جديد فقط
sudo mkfs -t xfs /dev/nvme1n1

sudo mkdir /data
sudo mount /dev/nvme1n1 /data
echo "hello from ebs" | sudo tee /data/test.txt
```

وأخيراً خذ لقطة من CloudShell:

```bash
aws ec2 create-snapshot \
  --volume-id vol-0123456789abcdef0 \
  --description "data volume before upgrade"
```

::: security نظّف بعد التجربة
الأقراص واللقطات تستمر تُحسب حتى بعد حذف السيرفر. احذف القرص الإضافي واللقطة والصورة لما تخلص، لأن القرص الإضافي ما ينحذف مع السيرفر.
:::

## الخلاصة

- **EBS** قرص دائم مربوط بمنطقة توفر، و`gp3` هو الخيار الافتراضي.
- **اللقطات** نسخ احتياطية، وهي الطريق لنقل قرص بين مناطق التوفر والمناطق.
- **AMI** تخلي السيرفر يقوم جاهز خلال ثوانٍ، وهذا أساس التوسّع السريع.
- **Instance Store** الأسرع، لكن بياناته تضيع مع الإيقاف.
- **EFS** للملفات المشتركة بين سيرفرات كثيرة، على لينكس.

بهذا نكمل قسم الخوادم. في [**الجزء السادس**](/posts/aws-06-load-balancers/) نبدأ قسم التوفر العالي: كيف توزّع الزوار على عدة سيرفرات بموزّع الحمل، فما يوقف موقعك لو تعطّل واحد منها.
